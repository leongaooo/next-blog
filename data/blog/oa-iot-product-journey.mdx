很多技术产品并不是从一个宏大的架构图开始的，而是从一个很朴素的问题开始：

**能不能让人、流程、设备和数据在同一个系统里真正协同起来？**

OA 解决的是组织协作问题，IoT 解决的是设备连接问题。它们看似分属两个世界：一个在办公室里流转审批、任务、通知和权限；一个在现场采集温度、能耗、状态、告警和位置。但当业务真的走到数字化深水区时，你会发现这两件事迟早会在同一个产品里相遇。

一边是人怎么决策，一边是设备发生了什么。中间缺的那座桥，就是产品要承担的价值。

## 从“流程在线”到“现场在线”

早期做 OA，最容易被看见的价值是把线下表单搬到线上。

请假、报销、采购、合同、用章、资产领用、工单流转，这些流程被电子化之后，效率确实提升了不少。至少不用再拿着纸质单据到处找人签字，也不用靠聊天记录反复追问“这个事情现在到哪一步了”。

但做着做着，我们会遇到一个更真实的问题：

**流程已经在线了，可现场仍然不在线。**

例如一张设备维修工单，OA 能记录谁提交、谁审批、谁处理、什么时候完成。但设备本身是否真的停机？故障发生前有没有异常数据？维修后运行状态是否恢复？这些关键事实如果还依赖人工填写，系统就只是“流程台账”，还没有成为“业务中枢”。

这就是 OA + IoT 的出发点。

OA 不再只是管人和流程，IoT 也不再只是采集设备数据。它们组合起来后，要回答的是：

- 设备异常能不能自动触发流程？
- 现场数据能不能成为审批依据？
- 工单处理能不能反向影响设备策略？
- 管理者看到的报表能不能同时解释“人做了什么”和“设备发生了什么”？

当这些问题开始被认真回答时，产品就从“工具”慢慢变成了“系统”。

## 产品视角：不要把两个系统硬缝在一起

OA + IoT 最容易走偏的方式，是把两个成熟系统粗暴拼接。

页面上加一个设备列表，流程里塞几个传感器字段，报表里放几张趋势图，看起来像是融合了，但用户仍然需要在两个心智模型之间来回切换。审批人看不懂设备数据，运维人员嫌流程太慢，管理者只看到一堆图表，却不知道该做什么决策。

真正的融合不是“OA 里有 IoT 页面”，而是让设备数据自然参与业务动作。

我更愿意把它拆成三个产品层次：

| 层次   | 关注点               | 典型能力                           |
| ------ | -------------------- | ---------------------------------- |
| 感知层 | 设备发生了什么       | 数据采集、状态监测、告警上报       |
| 协同层 | 谁来处理、怎么处理   | 工单、审批、通知、权限、SLA        |
| 决策层 | 为什么发生、如何优化 | 看板、趋势分析、策略调整、复盘报告 |

这个分层看似简单，但会直接影响产品设计。

如果只做感知层，系统会变成监控大屏；如果只做协同层，系统会变成传统 OA；如果只做决策层，系统又容易飘在管理报表里。OA + IoT 的难点，恰恰在于三层之间要形成闭环。

设备告警触发工单，工单处理沉淀知识，知识反过来优化告警规则。这个闭环一旦跑通，产品才真正开始有生命力。

## 技术视角：连接只是开始，建模才是核心

做 IoT 产品时，大家很容易把注意力放在协议接入上。

MQTT、HTTP、WebSocket、Modbus、OPC UA、边缘网关、设备影子、消息队列、时序数据库……这些当然重要，它们决定了数据能不能稳定上来。

但在 OA + IoT 的场景里，更难的是业务建模。

因为设备数据不是天然可理解的业务语言。

`temperature=82` 只是一个值。它代表正常、预警还是故障？要不要触发审批？要通知谁？是否与当前生产计划、空间位置、资产归属、保修状态有关？这些问题都不是协议层能回答的。

所以技术架构里需要有一层“业务语义转换”：

```text
设备数据 -> 数据清洗 -> 状态识别 -> 规则判断 -> 业务事件 -> 流程动作
```

举一个简单例子：

```js
const event = normalizeDevicePayload(payload)
const state = evaluateDeviceState(event)

if (state.level === 'warning') {
  await createWorkOrder({
    type: 'device-inspection',
    deviceId: event.deviceId,
    priority: state.priority,
    reason: state.reason,
    snapshot: event.raw,
  })
}
```

代码本身不复杂，复杂的是 `evaluateDeviceState` 背后的规则体系。

规则从哪里来？谁能配置？是否支持按组织、场景、设备类型差异化？规则变更后如何回溯？误报和漏报如何修正？这些才是产品长期演进时真正考验人的地方。

## 架构上要留出的几个位置

如果重新设计一个 OA + IoT 融合产品，我会很早就为几个模块预留清晰边界。

### 1. 设备身份与组织权限

OA 的权限通常围绕人、部门、角色、岗位展开；IoT 的权限则围绕设备、空间、项目、资产展开。

融合之后，权限模型不能只问“这个人能不能看这个页面”，还要问：

- 他能看哪些设备？
- 他能处理哪个区域的告警？
- 他能不能远程下发指令？
- 他审批的是费用，还是影响设备运行的策略？

设备权限一旦设计模糊，后期补救会非常痛苦。尤其是多组织、多园区、多项目的场景，权限边界必须从一开始就认真对待。

### 2. 事件中心

OA 里有流程事件，IoT 里有设备事件。两者最好汇聚到统一事件中心，而不是散落在各个业务模块里。

事件中心不只是消息转发，它应该承担事件标准化、事件追踪、事件订阅和事件重放能力。

这样当“设备离线 10 分钟”发生时，系统可以根据配置决定是创建工单、发送通知、升级告警，还是先观察一段时间。业务策略可以变化，但事件事实应该稳定存在。

### 3. 规则引擎

OA + IoT 的很多价值来自自动化，而自动化不能每次都靠开发改代码。

一个可运营的规则引擎，至少要支持：

- 条件组合：设备状态、时间窗口、空间位置、组织归属
- 动作编排：通知、工单、审批、外部接口调用
- 生效范围：全局规则、项目规则、设备类型规则
- 版本管理：规则变更可以追踪、回滚和审计

规则引擎不一定一开始就做得很重，但必须有演进方向。否则每一次客户定制都会变成一次代码分叉。

### 4. 数据分层

设备原始数据、实时状态、业务事件、流程记录、统计指标，最好不要混在一张表或一个概念里。

我更倾向于这样分：

- 原始数据：保留采集事实，用于排查和回放
- 状态数据：面向当前设备状态，用于页面展示和实时判断
- 事件数据：面向业务动作，用于触发流程和审计
- 指标数据：面向管理分析，用于报表和趋势

数据分层清楚之后，系统才不会在“实时查询”和“历史分析”之间互相拖累。

## 交付视角：现场永远会教育产品

真正进入交付阶段后，很多设计都会被现场重新检验。

文档里写着设备每 5 秒上报一次，现场可能因为网络环境变成 30 秒一次；协议里字段很标准，实际接入时某个厂家会多一个奇怪的状态码；产品设计里告警弹窗很醒目，但用户一天收到几百条之后只想全部关掉。

这时候最重要的不是证明原来的设计多么正确，而是快速建立反馈机制。

我在这类项目里越来越相信三件事：

### 第一，先跑通最短闭环

不要一开始就追求全场景覆盖。

先选择一个最有价值、边界清晰的场景，比如“设备异常自动生成巡检工单”。只要它能稳定跑通，就能验证采集、规则、流程、通知、权限、报表这一整条链路。

一个小闭环跑通，比十个大模块同时开发更能暴露真实问题。

### 第二，给人工干预留入口

自动化不是取消人工判断，而是减少无意义的人工搬运。

设备误报、临时停机、计划检修、网络波动，这些情况都会让系统判断出现偏差。所以产品需要允许用户确认、驳回、忽略、备注、合并和升级事件。

好的系统不是永远自动正确，而是在不确定时仍然可解释、可修正。

### 第三，不要让大屏成为唯一成果

很多 IoT 项目容易把大屏当作交付重点。大屏当然有展示价值，但它不是业务闭环本身。

真正有价值的是：

- 告警有没有被及时处理？
- 处理时长有没有下降？
- 设备故障是否能提前预警？
- 管理动作是否能追溯？
- 人员协作是否变得更顺畅？

如果这些问题没有改善，再漂亮的大屏也只是舞台灯光。

## 心态变化：从功能开发到产品经营

做 OA + IoT 这样的产品，最大的心路变化是：你会慢慢从“把功能做出来”转向“让系统长期可运营”。

功能开发关心的是这个按钮能不能点、这个流程能不能走、这个数据能不能展示。产品经营关心的是规则怎么配置、异常怎么处理、用户怎么接受、数据怎么沉淀、下一次迭代怎么更快。

这背后有几个认知变化。

### 从页面思维到事件思维

过去我们习惯从页面入口设计功能：列表、详情、表单、审批页。

但 OA + IoT 更适合从事件出发：什么事情发生了？谁需要知道？系统应该自动做什么？人需要在哪里介入？

事件思维会让产品更接近业务真实流动。

### 从一次性交付到持续调参

IoT 场景里没有一劳永逸的规则。

设备会老化，环境会变化，业务会调整，用户也会逐渐形成新的使用习惯。产品上线只是开始，后续的规则调优、阈值修正、流程优化和数据分析才是长期价值所在。

### 从技术正确到业务可信

技术上能采集到数据，不代表业务上信任这些数据。

用户会问：这个数据准吗？为什么触发告警？为什么派给我？为什么这次没有提前提醒？这些问题如果回答不了，系统就很难真正进入日常工作。

所以可解释性、审计记录、数据来源、规则版本，都是产品信任的一部分。

## 一个更理想的 OA + IoT 产品形态

我理想中的 OA + IoT，不是一个堆满菜单的后台系统，而是一个围绕业务事件运转的协同平台。

设备负责说出事实，规则负责识别含义，流程负责组织行动，数据负责沉淀经验。

它应该让一线人员少填表，让管理人员少追问，让技术人员少救火，让组织对现场状态有更稳定的感知。

如果用一句话总结它的价值，我会这样说：

**OA + IoT 的本质，是把“设备的状态”转化为“组织的行动”。**

这件事听起来朴素，却很难。难在技术链路长，难在现场变量多，难在组织协同复杂，也难在产品必须同时理解机器和人。

但也正因为难，它才值得做。

## 写在最后

回头看 OA + IoT 的产品过程，我越来越觉得它不是单纯的技术集成，而是一场关于“连接”的练习。

连接设备与流程，连接现场与管理，连接数据与决策，连接系统能力与人的真实工作。

当一个告警不再只是红色数字，而是能自动进入工单、找到负责人、记录处理过程、沉淀复盘结论时，技术才真正从后台走进业务。

这大概就是做技术产品最有意思的地方：

我们写下的每一行代码，最后都应该帮助现实世界少一点混乱，多一点秩序。
